# Butler × DeepSeek Harness 插件搬运 — 开发方案 v2.0

> 版本：v2.0（2026-11-14，汇总全部讨论结论，取代 v1.0）
> 定位一句话：**不是把 Butler 接入 dsh，而是把 dsh 插件市场的有用插件"搬运"进 Butler——下载即用，插件能力并入 Butler 调度，用户全程无感知。**

---

## 0. 方案摘要

| 项 | 结论 |
|----|------|
| 要做什么 | 让 Butler 能下载 DeepSeek Harness（dsh）插件市场的插件并直接使用 |
| 核心认知 | 插件兼容性取决于**运行时契约**（Cordis API），不是"同用一个大模型"；dsh 插件 = TypeScript 程序，必须有宿主运行时才能跑 |
| 怎么实现 | Butler 内嵌一个 **DSH 宿主**（Node 运行时，自动部署），中间加一条 **通道连接器**（独立 daemon，Go 编写，纳入 BHL 链路） |
| 用户体验 | `butler skill install <插件名>` → Butler 的 LLM 直接多一个能力；dsh 对用户完全透明 |
| 不做什么 | 不用 dsh 的执行循环、Web UI、模型接入层——以 Butler 自己的为准 |
| 周期 | 约 8~10 周（P1 MVP 2~3 周即可见价值） |

---

## 1. 目标与边界

### 1.1 目标（按优先级）

- **G1（核心）**：Butler 可下载/安装/卸载 dsh 插件市场的插件，插件工具并入 Butler 的 LLM 工具表，像原生 skill 一样调用
- **G2**：第三方插件的安全管控（权限审批、沙箱、一键禁用、故障隔离）
- **G3**：SKILL.md ⇄ dsh 插件描述双向映射（技能模型统一，为后续 Butler Skill 反向导出铺路）
- **G4（可选，后续）**：Butler Skill 导出为 dsh 插件，发布到 dsh 生态

### 1.2 明确不做

- 不在 Python 里复刻 Cordis 微内核（成本不可控）
- 不用 dsh 的 Agent 执行循环（Butler 有自己的编排器）
- 不用 dsh 的 Web UI（Butler 有 2x2 玻璃拟态 UI）
- 不用 dsh 的模型接入层（Butler 有自己的 DeepSeek Key 链路）
- UI/皮肤类插件不适配（改的是 dsh 自己的界面，对 Butler 无意义）

---

## 2. 关键认知（本方案的立论基础）

1. **"同属一个大模型不会出问题"不成立。** 插件是调 `ctx.tools`/`ctx.llm`/`inject` 这些宿主 API 的 TypeScript 代码，模型只是"大脑"，"手脚"是 dsh 运行时给的。同模型 ≠ 同运行时。
2. **dsh 插件不是独立程序，是"框架的寄生模块"。** 没有 `main` 函数，必须嵌在 Cordis 微内核宿主里才能活。所以"用插件"必须连宿主一起搬。
3. **"DSH 宿主"不是一台机器**，就是 `@deepseek-ai/dsh` 这个 npm 包（Node 程序），类比"VS Code 之于 VS Code 插件"。体积小、可隔离部署、可自动拉起。
4. **TS 加入 Butler 符合 BHL 混合编程哲学。** 你的 C++/Go/Rust 是"自带 main 的独立进程 + 协议链路"；Node 这条链路同构——进程里装着 Node 运行时 + Cordis 宿主 + 插件，是 BHL 的新成员，地位与 Go 执行器相同。

---

## 3. 总体架构

```
用户视角：  butler skill install doc-reader → Butler 多了个能力 ✅（dsh 无感知）

实际链路：
┌────────────┐  北向接口        ┌───────────────────────┐  南向接口       ┌─────────────────────────┐
│  Butler    │ ←— Unix socket → │  butler-dsh-          │ ←— stdio/socket→│  DSH 宿主 (Node 子进程)   │
│  (Python)  │   JSON-RPC/TLV   │  connector (Go daemon)│   JSON-RPC    │  Cordis + 市场插件(190+)  │
└────────────┘                  └───────────────────────┘                 └─────────────────────────┘
     ▲                                   │                                        ▲
     │                                   ├── 权限代理（高危操作过 Butler 审批）        │
     │                                   ├── 能力注册表（工具清单双向同步）            │
     └── Butler 侧与 C++/Go/Rust BHL 照旧 ─┴── 生命周期监管（崩溃拉起/健康检查）     └── 插件装在这里跑
```

- **Butler（Python）**：编排器、LLM、记忆库、原生 skills —— 几乎不动
- **连接器（Go daemon）**：新增的"通道程序"，双语翻译官，自身无业务逻辑
- **DSH 宿主（Node）**：插件发动机，打包进 Butler 便携部署（`lib_external/`），由连接器自动拉起，用户不可见

### 3.1 DSH 宿主内部 → Butler 取舍表

| 宿主组件 | 对 Butler | 说明 |
|---------|----------|------|
| 插件加载器 + Cordis 微内核 | ⭐ 采用 | "能跑市场插件"的核心零件 |
| 权限审批 + 沙箱 + Guard | ⭐ 采用 | 第三方插件的管控底盘 |
| Session Log（只追加会话日志） | ⭐ 采用 | 插件调试回放神器；映射为 Butler 事件 |
| tools/pre-execute 拦截器 | ⭐ 采用 | 接 Butler Self-Healing |
| MCP 客户端 | 可选 | 免费福利，可作为补充工具源 |
| 内置工具（文件/Shell/终端） | 以 Butler 为准 | 能力重叠 |
| Agent 执行循环 / Web UI / 模型接入 | 不用 | Butler 自有 |

## 4. 通道连接器设计（`butler-dsh-connector`）

### 4.1 定位

独立进程（Go 编写，单二进制、零依赖、符合便携模式），BHL 链路新成员。只做"通道"：翻译、路由、监管，不做业务。

### 4.2 五大模块

| 模块 | 职责 |
|------|------|
| 1. 能力注册表 | 启动握手收集插件工具清单（name/schema/description），北向注册进 Butler 工具表；装卸增量同步 |
| 2. 调用路由器 | Butler 工具调用 → `tool_call_id` 路由南下 → 结果（含流式 chunk）回填 |
| 3. 事件泵 | dsh Session Log 事件、插件状态、拦截请求 → 推给 Butler；反向注入 |
| 4. 权限代理 | Shell/文件写等高危操作拦截 → Butler 审批 → 放行/拒绝 |
| 5. 生命周期监管 | 拉起/守护两侧进程、崩溃自动重连、优雅退出、健康检查（供 `butler doctor`） |

### 4.3 协议（一次冻结，向后兼容）

控制面 JSON-RPC over Unix socket（Windows 用 named pipe）；数据面（音频/文档字节流）复用 Butler 现有 TLV 帧。

```json
{
  "id": "call-001",
  "type": "tool.invoke",          // tool.invoke | tool.result | event.push | registry.sync | approve.ask ...
  "payload": { "tool": "doc-reader", "args": { "path": "report.pdf" }, "stream": true },
  "ts": 1763124960
}
```

### 4.4 为什么独立进程

故障隔离（插件崩了不拖垮 Butler）、语言自由（换实现两端不动）、可做 golden-file 契约测试、与 BHL 运维心智统一。

## 5. 插件市场下载与安装（G1 核心流程）

### 5.1 dsh 官方安装链路（已核实）

```bash
dsh plugin --profile web add dshmarket       # 添加市场源
dsh plugin --profile web update              # 更新索引
dsh plugin --profile web search doc-reader   # 搜索
dsh plugin --profile web install doc-reader  # 安装
```

插件包 `.dshp` 格式；来源支持：dsh-market、npm、`github:仓库`、本地路径。社区目录：dsh-plugins.org、`dsh-plugin-discovery`、`tanle-mtr/dsh-plogin-plugin-recommender`（190+ 插件 / 12 分类）。

### 5.2 Butler 封装（用户唯一入口）

```bash
butler skill install doc-reader    # 命名走 Butler 风格（也可 butler plugin install）
# 内部：市场下载 → DSH 宿主挂载（自动生成 cordis.yml Patch）
#      → 能力注册表同步 → Butler LLM 可发现/可调用
butler skill disable <name>        # 一键禁用（不卸载）
butler skill uninstall <name>      # 干净卸载（Effect 自动回收）
```

### 5.3 安装前体检（内置分类过滤 + 冲突检测）

| 插件类型 | 例子 | 策略 |
|---------|------|------|
| 工具/Skill 类 | doc-reader、数学建模、代码检索 | ✅ 直接装，核心目标 |
| 能力 Provider 类 | memory、远程执行、vision-router | ⚠️ 过冲突检测（与 Butler 记忆库/模型链路冲突者提示接管方） |
| 模型接入类 | code-provider、free-model | ⚠️ 默认禁用（与 `DEEPSEEK_API_KEY` 链路冲突） |
| UI/皮肤类 | sidebar、skin、wallpaper | ❌ 不适配，过滤隐藏 |

外加：来源白名单（市场/npm/指定 GitHub org）、平台检查（标死 bash//tmp 的插件在 Windows 拦截）、`dsh --dump-config` 残留检查。

## 6. 兼容性风险清单与防护网

### 🔴 一定会遇到

1. **dsh API 破坏性变更**（Developer Preview）→ 钉版本（`@deepseek-ai/dsh@具体版本`）；dsh 调用收敛在连接器/宿主两处；CI 版本冒烟；升级/回滚流程进 `butler doctor`
2. **模型工具选中率稀释**（装太多插件）→ 按需启用、禁用优先于卸载、触发率抽测（目标 ≥80%）

### 🟡 可能遇到

3. **平台兼容**（Win/Linux/macOS）→ 安装前平台检查；Windows CI 冒烟（named pipe）
4. **能力冲突**（dsh memory vs Butler 记忆库等）→ 冲突检测 + 接管方声明
5. **运行环境**（Node LTS、原生 npm 依赖）→ Node 一并隔离进 `lib_external/`；`butler doctor` 增加环境项

### 🟢 基本没问题

6. **插件之间共存**：Cordis DI + Effect 自动回收天然支持多插件
7. **纯工具类插件**：dsh 版本对、平台对即稳

### 安全（贯穿）

- 插件能执行 Shell/改文件（SDK 示例默认 `danger-full-access`）→ 权限代理统一审批，只读自由/写执行需批
- 密钥只走 `${VAR}` 环境变量，不落盘明文；shim/插件包不携带 Key

## 7. 分阶段实施计划

### P0 调研对齐（1 周）
- 跑通 dsh 环境 + `dsh --dump-config` 存档；最小 `hello-plugin` + `greet` 工具验证 Cordis 链路（inject/zod/Session Log 回放）
- 产出：《插件分类清单 × Butler 能力对照表》（细化 §5.3 / §3.1）
- ⚠️ 全程隔离目录/容器

### P1 MVP：连接器 + 单插件打通（2~3 周）⭐ 价值里程碑
- `butler-dsh-connector` Go daemon 最小版：能力注册表 + 调用路由 + 生命周期
- 桥协议冻结（golden-file 契约测试）
- DSH 宿主接入 Butler 便携部署（`dependency_manager.py` 扩展，Node + dsh 隔离安装）
- `butler skill install` 命令最小流程
- **验收**：dsh 市场装一个真实插件（如 doc-reader），Butler 对话中成功调用，Session Log 完整记录

### P2 安全与兼容防护网（2~3 周）
- 权限代理（审批管线 ↔ Butler 权限矩阵）
- 安装前体检：分类过滤 + 冲突检测 + 平台检查 + 来源白名单
- 一键禁用/回滚；`butler doctor` 插件健康检查
- Self-Healing 接 `tools/pre-execute`；记忆库接 Session Event（冲突接管声明）
- **验收**：故障注入（杀 Node/杀插件）不拖垮 Butler；恶意/越权操作被拦截

### P3 生态体验（2 周）
- 插件搜索/列表/更新命令（`butler skill search|list|update`）
- 触发率调优：按需启用、技能推荐筛选
- SKILL.md ⇄ dsh descriptor 双向转换器（G3）
- **验收**：20 条自然语言样本工具选中率 ≥80%；装卸 24h 长跑无泄漏

### P4 稳定化与发布（1~2 周）
- 兼容矩阵 CI（dsh 版本 × 插件 × 三平台）
- 文档：插件使用指南、SKILL.md 描述质量规范（description 决定触发率）
- （可选 G4）`butler skill export` 导出 Butler Skill 为 dsh 插件

**总计约 8~10 周**（单人全职口径）。

## 8. 目录结构建议

```
Butler/
├── butler/                        # 现有编排器（不动）
├── skills/                        # 现有 One Folder = One Skill（不动）
├── connector/                     # 【新增】butler-dsh-connector（Go，仅源码）
│   ├── cmd/dsh-connector/         # 入口
│   ├── internal/                  # proto/registry/events/approval/supervisor/transport/north/south/config
│   ├── butler_dsh/client.py       # Python 北向客户端
│   └── docs/protocol.md           # 协议规范 v1（字节级冻结）
├── dsh-host/                      # 【新增】DSH 宿主 shim（TS，仅源码）
│   ├── src/                       # protocol/codec/registry/risk/host-adapter/cordis-host/server
│   ├── test/                      # 28 项测试（含 Go golden 跨语言契约）
│   └── bin/server.ts              # 入口
├── integration/                   # e2e 全链路验证（12 项断言）
├── .github/workflows/release.yml  # CI：tag 时构建三平台产物 → GitHub Releases
├── docs/dsh-adapter/              # 对照表、协议、使用指南
└── .gitignore                     # bin/ dist/ node_modules/ lib_external/ logs/

安装期生成（不进仓库，对齐 lib_external/ 便携模式）：
lib_external/dsh-connector/        # ← GitHub Releases 按平台下载的预编译二进制（或源码 go build）
lib_external/dsh-host/             # ← npm run build 产物（dist/，零运行时依赖）
```

**产物生成策略（仓库零二进制）**：源码仓库只放代码；`.github/workflows/release.yml` 在打 tag 时自动构建 Linux/macOS/Windows 三平台连接器二进制并上传 GitHub Releases；`install.sh` / `dependency_manager.py` 扩展在安装期按平台拉取二进制 + `npm run build` 生成 shim 产物，全部隔离进 `lib_external/`。用户机器无需 Go，仅需 Node.js ≥ 20。

## 9. 测试与验收标准

1. **契约测试**：连接器协议 golden-file（请求/响应/流式/错误帧）
2. **插件冒烟**：每个安装插件在 Butler 内完成 1 次真实调用（Session Log 落盘）
3. **触发率抽测**：20 条自然语言样本，工具选中正确率 ≥80%
4. **卸载干净性**：`--dump-config` 无残留、Effect 全回收、24h 长跑无泄漏
5. **故障注入**：杀 Node / 杀插件 / 断连，自动重连与会话恢复
6. **安全用例**：越权 Shell/文件写被拦截；明文 Key 扫描为零
7. **平台矩阵**：Linux / macOS / Windows × dsh 当版与前一版

## 12. 一句话总结

**把 dsh 当"插件发动机"整体搬进 Butler（自动部署、用户无感知），中间架一条 Go 通道连接器（BHL 新成员）做翻译与管控；用户只看到 `butler skill install` 一条命令，装完插件就是 Butler 自己的能力。风险靠"版本钉死 + 安装体检 + 权限代理 + 一键禁用"四件套兜住。**
